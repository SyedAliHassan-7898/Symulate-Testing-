# k6 Load & Performance Testing

k6 tests run **separately** from the Playwright suite - they exercise the
API and frontend routing layer under load, plus one real-headless-browser
scenario. Every run produces CSV, a log, a JSON summary, and k6's own
built-in HTML report; a live Grafana dashboard is optional on top of that.

## Test coverage

| Layer | Script | Covers |
|---|---|---|
| API + Frontend routes | `k6/scenarios/api-smoke.js` | Every entry in `ENDPOINTS` (API) and `FRONTEND_ROUTES` (UI pages) - see `k6/lib/config.js`. Fast pass, ~30s. |
| API + Frontend routes | `k6/scenarios/load-test.js` | Same endpoint list, under ramping load (0→25 VUs) to catch throughput/latency regressions. |
| Real browser | `k6/scenarios/browser-login.js` | Headless Chromium driving the actual login → dashboard flow - the only scenario that exercises real page rendering/JS. |

`ENDPOINTS` and `FRONTEND_ROUTES` in `k6/lib/config.js` are the single
source of truth for what gets load-tested - add a route there and every
scenario (and the Grafana dashboard's per-URL panels) picks it up
automatically. This is the project's load-test "coverage list": expand it
as real backend/frontend routes are added.

## Running

```bash
npm run k6:smoke     # API + UI routes, fast pass (~30s)
npm run k6:load      # same routes, ramping load (~2 min)
npm run k6:browser   # headless-Chromium UI flow
npm run k6:all       # all three, in order
```

This is intentionally separate from Playwright - see the root
[`README.md`](../README.md) for `npm run test:all:full` (Playwright only)
vs `npm run test:all` (Playwright + full k6 suite).

Every run writes to `k6/results/` (gitignored):

```
k6/results/<scenario>-<timestamp>.csv               # raw metric samples
k6/results/<scenario>-<timestamp>.log                # full console output
k6/results/<scenario>-<timestamp>-summary.json       # machine-readable summary
k6/results/<scenario>-<timestamp>-report.html        # k6's own built-in HTML report
```

Open the `-report.html` file directly in a browser - no setup, works fully
offline.

## Real hit URLs, not generic labels

Every request is tagged with its real endpoint name/URL (`ENDPOINTS`,
`FRONTEND_ROUTES`), so the terminal summary, CSV, JSON summary, and Grafana
dashboard all break results down per actual route instead of one lumped
bucket.

## Live Grafana monitoring dashboard

For real-time monitoring while a test runs, see
[`docs/GRAFANA.md`](GRAFANA.md) - either the hosted **Grafana Cloud k6**
option (no Docker) or a local **Docker Grafana + InfluxDB** stack:

```bash
npm run grafana:up              # local stack
npm run k6:smoke:grafana         # or :load:grafana / :browser:grafana / :all:grafana
# open http://localhost:3000
```

```bash
k6 login cloud                    # hosted, one-time
npm run k6:smoke:cloud
```

Both are optional - if neither is set up, `k6/run.js` warns and continues
normally; CSV/log/summary/HTML report are never blocked by Grafana/cloud
availability.

## Running the whole suite inside Docker (avoids host memory issues)

If your machine struggles to run Chromium + k6 natively (low RAM, Docker
Desktop instability, etc.), run everything inside an isolated container
instead - see [`docs/DOCKER.md`](DOCKER.md):

```bash
npm run docker:build
npm run docker:test
```

## Running in CI / on every deployment

`.github/workflows/deploy-tests.yml` runs Playwright (entire suite,
headless) and the full k6 suite as two **separate, parallel** jobs on
every push to `main` and successful deployments. Both upload their results
(HTML report / CSV+log+summary+HTML) as build artifacts.

Repository secrets needed: `BASE_URL`, `API_URL`, `SUPER_ADMIN_EMAIL`,
`SUPER_ADMIN_PASSWORD`.

## Thresholds

Shared thresholds live in `k6/lib/config.js` (`DEFAULT_THRESHOLDS`):
`http_req_failed` rate < 1%, `http_req_duration` p95 < 1500ms, `checks`
pass rate > 99%. Tune these as the app's real-world baseline becomes
clearer.
